## iter40 — Персистентность политики кампании (П1, блокер)

Без этого шага любой UI-ввод последующих шагов бессмыслен: save/load
молча откатит сэмплер/оптимизатор на бокс и перестанет писать
`spec_hash`/`campaign` в `origin_tag` новых точек.

**Файл:** `src/apps/campaign_state.py`.

`runner_to_state` — добавить в раздел `"runner"`:

```json
"phr_spec": [<PhrSpec.to_dicts()>] | null,
"campaign_label": "<str>" | "",
"preflight_pairs": [[["осьA1", ...], ["осьB1", ...]], ...]
```

`runner_from_state` — восстановление ШТАТНЫМИ сеттерами (они валидируют
против схемы): `set_phr_spec(PhrSpec.from_dicts(...))`,
`set_campaign_label(...)` (только непустая), `set_preflight_pairs(...)`.
Старые сейвы без ключей → `None` / `""` / `[]` (без ошибок — как
`sampling_groups` iter31).

**Инварианты (тесты, `test_iteration40_campaign_policy_persistence.py`):**

1. round-trip phr-спеки: `spec_hash()` до сохранения == после загрузки
   (референс — `RECIPE_DICTS` из тестов iter35, hash
   `049d0e35…360450`);
2. round-trip `campaign_label` + `preflight_pairs` (включая оси-суммы
   `["PMPlus_8", "DL_531"]`);
3. старый сейв (без новых ключей) грузится, поля пустые;
4. точка, добавленная ПОСЛЕ load, получает `spec_hash`/`campaign`
   в `origin_tag` (сквозной сценарий save → load → добор);
5. `preflight()` после load видит пары (pair-coverage не пустой).

## iter41 — Сетап: ввод phr-спеки + паспорт кампании (П2, П3)

**Файлы:** `src/apps/campaign_ui.py` (`render_setup_form`,
`render_composition_bounds`, `setup_prefill_from_runner`,
`project_settings_dataframe`/`render_project_settings`) + чистые хелперы.

### 41.1 Третий режим ввода состава: «phr-спека (JSON)»

В радио «Способ ввода» (`render_composition_bounds`) добавить режим
**«phr-спека (JSON)»**: `st.text_area` с JSON-списком узлов в формате
`PhrSpec.from_dicts` (тот же формат, что `to_dicts` → входит в hash) +
опциональный `st.file_uploader` (.json). Конструктор `PhrSpec` уже
делает статическую валидацию (циклы, ссылки, пустые пересечения) —
ошибки показывать `st.error` как есть.

Чистые хелперы (тестируемые):

* `parse_phr_spec_json(text: str) -> PhrSpec` — json.loads + from_dicts,
  человекочитаемые ошибки;
* `phr_spec_summary_dataframe(spec) -> pd.DataFrame` — узел / режим /
  lo / hi / ref / cap_to / cap_ratio / «компонент смеси?» (лист);
* показ `spec.phr_intervals()` и `spec.fraction_bounds()` (рассчитанные
  доли для mixture-блока — аналог таблицы режима «Массовые части»).

Связка при «🏗 Построить проект» в этом режиме:

* **имена компонентов смеси берутся из `spec.component_names`** (поле
  «Компоненты смеси» игнорируется/заполняется от спеки с подписью) —
  иначе рассинхрон имён, и раннер молча (warning) откатится на бокс;
* mixture-блок схемы — из `spec.fraction_bounds()`;
* после сборки раннера — `runner.set_phr_spec(spec)`;
* функциональные группы (iter31) в этом режиме НЕ применяются к
  сэмплингу (при заданной спеке `_phase_candidates` идёт phr-путём) —
  поле групп скрыть/подписать.

### 41.2 Паспорт кампании (сетап, до первого замера)

Секция «🪪 Паспорт кампании» в форме сетапа (и доступна после сборки):

* «Метка кампании» (`st.text_input`) → `runner.set_campaign_label`;
* «Обязательные 2D-пары» (`st.text_area`) → `runner.set_preflight_pairs`.
  Формат: одна строка = пара, стороны через `|`, ось-сумма — имена
  через запятую:

  ```
  UV_CSFCP | TiO2_BLR895
  dT | PMPlus_8, DL_531
  DINP | TiO2_BLR895
  ```

  Чистые хелперы `parse_preflight_pairs(text)` /
  `preflight_pairs_to_text(pairs)` (round-trip, образец —
  `parse_sampling_groups`/`sampling_groups_to_text`);
* показ `spec_hash` активной спеки (`st.code`, полный hex) с подписью
  «зафиксируйте хеш и лоты сырья ДО первого замера (CAMPAIGN_SPEC_PVC §3)».

### 41.3 Отражение после загрузки

* `setup_prefill_from_runner`: + `campaign_label`, `preflight_pairs`
  (текст), режим «phr-спека» с JSON `to_dicts`, если спека активна;
* `project_settings_dataframe`/`render_project_settings`: + строки о
  phr-спеке (q, dim_z, hash-префикс 12 симв.), метке, парах.

**Тесты (`test_iteration41_setup_phr_ui.py`):** парсинг JSON
(валид/ошибка конструктора наружу), summary-таблица на референсной
спеке iter35, `parse_preflight_pairs` round-trip (+ оси-суммы),
prefill из раннера с активной спекой, «имена из спеки» при сборке.

## iter42 — Слой навески: phr, квантование, премикс (П4) — ✅ СДЕЛАНО

**Файлы:** `src/design/phr_sampler.py` (одна новая функция),
`src/apps/campaign_ui.py` (таблицы seed/рецепта).

### 42.1 Логика: доли → phr

Новый метод `PhrSpec.fractions_to_phr(x) -> np.ndarray` (обратное к
`to_fractions`): масштаб от fixed-листа (`T = value_fixed / x_fixed`;
если fixed-листа нет — ValueError с объяснением, что тотал неопределим).
Тест: round-trip `fractions_to_phr(to_fractions(p)) == p` на
референсном anchor iter35.

### 42.2 UI: ввод разрешения весов

В секциях seed-дизайна и рецепта ветки (при АКТИВНОЙ phr-спеке):
поля «шаг весов, г» и «г на 1 phr» → `delta_phr = шаг / (г/phr)`
(показ рассчитанного δ; пример из CAMPAIGN_SPEC_PVC §5: 0.1 г,
5 г/phr → δ=0.02).

### 42.3 Чистый хелпер таблицы навески

`recipe_weighing_dataframe(spec, x_fractions, delta_phr)`:

| колонка | источник |
|---|---|
| компонент | `spec.component_names` |
| phr nominal | `fractions_to_phr(x)` |
| phr actual | `quantize_recipe(p, δ).p_actual` |
| граммы actual | `p_actual · г/phr` |
| премикс | `premix_required(δ, lo, hi)` по `phr_intervals()`; fixed-оси — «—» |
| нарушение | строки `violations`, относящиеся к узлу (пусто = ок) |

Подпись обязательна (CAMPAIGN_SPEC_PVC §5): **«дозируйте и фиксируйте
ФАКТИЧЕСКИЕ значения (actual); модель должна видеть actual, а не
nominal»**. `violations` показывать как `st.warning` (A0.6 — не
блокировать).

### 42.4 Интеграция

* `branch_recipe_dataframe`/`…excel_bytes`: при активной спеке и
  заданном δ — добавить лист/колонки навески (nominal/actual/премикс);
* `seed_design_dataframe`/`…excel_bytes`: то же для каждой строки плана;
* **фиксация actual**: при активной спеке и заданном δ предложенный
  план ПЕРЕД показом снапится к δ-сетке (`quantize_recipe` построчно),
  и `commit_seed`/`commit_measured` получают actual-доли
  (`to_fractions(p_actual)`) — с явной подписью, что зафиксирован
  actual-план. Violations не блокируют, но показываются.

**Тесты (`test_iteration42_weighing_ui.py`):** round-trip 42.1;
таблица навески на референсной спеке (SBM_55/UV_CSFCP → премикс,
DINP → прямая — golden §5); violations прокидываются; снап плана
перед фиксацией меняет X на actual.

### Что зафиксировано реализацией (06.08.2026): 21 тест + регресс 274

1. **42.1** — `PhrSpec.fractions_to_phr(x, tol=1e-6)`: масштаб от ПЕРВОГО
   fixed-листа с `value > 0` (якорь); ОСТАЛЬНЫЕ fixed-листья работают
   ПРОВЕРКОЙ согласованности (расхождение = «доли не из этой спеки»,
   явный `ValueError`, как в `encode`). Без fixed-листа — ошибка с
   объяснением («Σphr по долям НЕОПРЕДЕЛИМ»), не молчаливое «принято 100».
   Вход нормируется на `Σx` (после clip/quantize сумма может уехать),
   поэтому якорь воспроизводится точно; принимает и (q,), и (n × q).
2. **42.2** — `weighing_delta_phr(step_g, grams_per_phr)`, golden §5:
   0.1 г / 5 г·phr⁻¹ → δ = 0.02 phr; оба аргумента строго > 0.
3. **42.3** — `recipe_weighing_dataframe` построена ПОВЕРХ `point_report`
   (iter49), логика навески НЕ дублируется: nominal / actual / граммы /
   премикс («—» = правило неприменимо на fixed-осях) / нарушение (строки
   `violations` этого узла). `weighing_caption` — δ + список осей на
   премикс + обязательное требование фиксировать actual.
4. **42.4** — `snap_design_to_grid(spec, X, δ)` (ИДЕМПОТЕНТЕН; процесс-оси
   не трогает) + `seed_weighing_dataframe` в ДЛИННОМ формате
   («опыт × компонент», а не 3·q колонок: при q≈19 широкая таблица
   нечитаема) + опциональный лист «Навеска» в `seed_design_excel_bytes`
   (kwargs `spec`/`delta_phr`/`grams_per_phr` — прежние вызовы не сломаны).
5. **UI seed-цикла**: экспандер «⚖️ Навеска (phr)» появляется ТОЛЬКО при
   активной спеке, имена которой совпадают с mixture-осями фазы; поля «шаг
   весов»/«г на 1 phr» → δ; при δ>0 план СНАПАЕТСЯ к сетке ДО показа и
   фиксации (открытый вопрос 2 закрыт: дефолт actual + caption, без
   переключателя), карта навески — по выбранному опыту; violations —
   `st.warning`, фиксация НЕ блокируется (A0.6). Шаг весов или загрузка = 0
   ⇒ слой выключен, план фиксируется как nominal (сказано подписью).
6. Рабочий стол ветки (навеска для x*) в этот шаг НЕ входил — остаётся
   при следующем проходе по рецепту ветки.

## iter43 — Постановка откликов: пороги, chance, binding (П5) — ✅ СДЕЛАНО


**Файлы:** `src/apps/mixture_process_runner.py` (хранилище chance),
`src/apps/campaign_state.py` (персистентность), `src/apps/campaign_ui.py`
(редакторы целей + показ binding_report).

### 43.1 Хранилище chance-ограничений ветки

По образцу ценовой ноги (`_branch_cost` — runner-level, сериализуется
в campaign_state):

* `runner.set_branch_chance(branch_id, {prop: ChanceConstraint})`
  (+ геттер/очистка; валидация prop против `property_names`);
* `optimize_xbest` при наличии сохранённых chance для ветки подставляет
  их в `chance_constraints=` АВТОМАТИЧЕСКИ (явный аргумент вызова
  имеет приоритет);
* персистентность: `"branch_chance": {bid: {prop: {"y_min":…, "y_max":…,
  "alpha":…}}}` (asdict/распаковка `ChanceConstraint` — dataclass),
  round-trip тест.

### 43.2 Редакторы целей: новые виды

В обоих редакторах (создание ветки `render_branch_creation` и
«🎯 Редактор целей ветки») selectbox «вид» расширить:

* `max` / `min` / `target` — как есть;
* **«порог ≥» / «порог ≤»** — ввод: порог + СКО шума измерения
  (`noise_sd > 0`); построение — `hard_threshold_spec(threshold,
  noise_sd, "ge"/"le")` → обычный `DesirabilitySpec` (persists штатно).
  Подсказка: ramp = шум измерения, НЕ «узкий» (iter39, замечание 1);
* **«вероятностный Pr(y ≤ max) ≥ 1−α»** — ввод: `y_max` (и/или `y_min`),
  `alpha` → `ChanceConstraint` через `set_branch_chance` (43.1).
  В таблице целей ветки chance-ограничения показывать ОТДЕЛЬНЫМ блоком
  (это множитель к d_overall, не цель).

`draft_add_goal`/`goal_editor_dataframe` расширить соответственно
(чистые — тестируются напрямую).

### 43.3 binding_report — обязателен к просмотру

Чистый хелпер `binding_report_dataframe(report) -> pd.DataFrame`
(ограничение / тип (veto|chance) / % точек пула под биндингом /
значение в x* / порог). Показ:

* после «Рецепт ветки» (`branch_recipe_dataframe` возвращает и report —
  либо отдельная функция `branch_recipe_with_binding(...)`, чтобы не
  ломать сигнатуру/Excel);
* caption-строка: «оптимум не найден» vs «оптимум запрещён»
  (CAMPAIGN_SPEC_PVC §7).

**Тесты (`test_iteration43_goal_ui.py`):** set_branch_chance +
персистентность round-trip; `optimize_xbest` подхватывает сохранённые
chance (binding_report непустой); билдер «порог» выдаёт спеку
`hard_threshold_spec`-эквивалент; `binding_report_dataframe` структура.

### Что зафиксировано реализацией (06.08.2026): 18 тестов + регресс 100

1. **43.1** — `runner._branch_chance` (runner-level, как `_branch_cost`;
   `Branch` не тронут) + `set_branch_chance` / `branch_chance` (геттер отдаёт
   КОПИЮ). `optimize_xbest` подставляет сохранённые ограничения при
   `chance_constraints=None`; ЯВНЫЙ аргумент главнее, включая пустой `{}`
   («на этот вызов без ограничений»). Валидация: имя отклика против
   `property_names`, тип `ChanceConstraint`, существование ветки.
2. **43.1 персистентность** — `"branch_chance"` в `campaign_state`;
   `±inf` пишется как `null` (а НЕ литералом `Infinity`: иначе файл
   перестаёт быть валидным JSON для внешних читателей) и восстанавливается
   в `∓inf`. Старый сейв без ключа грузится как «ограничений нет».
3. **43.1 обратимость** — `CampaignController.set_chance` через штатный
   `_apply` (снимок → мутация → re-score → undo). `chance` добавлен в
   `_snapshot`/`_restore`: без этого откат правки целей оставлял бы прежний
   argmax-контекст, и «рекомендация сместилась X→Y» врала бы. Ограничение —
   НЕ цель: `goal`, роли и ИЗМЕРЕННЫЙ `d_best` не меняются, эффект виден
   только в argmax/binding.
4. **43.2** — чистый билдер `build_goal_spec(kind, …)`: `GOAL_KINDS =
   [max, min, target, «порог ≥», «порог ≤»]`; порог → `hard_threshold_spec`
   (golden: порог 10 при шуме 0.5 → `max[9.5, 10]`). Черновик хранит СЫРЫЕ
   входы (`threshold`/`noise_sd`), спеки собирает `draft_goal_specs` —
   ошибка вида всплывает при ДОБАВЛЕНИИ цели, а не при создании ветки.
   Chance-черновик: `draft_add_chance` / `draft_remove_chance` /
   `draft_chance_constraints` (`None` границы → `∓inf`, валидация сразу).
5. **43.2 UI** — редактор целей ветки: расширенный selectbox видов + поля
   «порог»/«СКО шума» с подсказкой (ramp = шум измерения, iter39 зам. 1) +
   ОТДЕЛЬНЫЙ блок вероятностных ограничений (`chance_editor_dataframe`,
   `ctrl.set_chance`) — не в таблице целей: смешение врало бы про роль
   отклика (§5). В форме СОЗДАНИЯ ветки виды пока прежние (пороги/chance
   задаются в редакторе после создания) — хвост на iter44/50.
6. **43.3** — `branch_recipe_with_binding` (рецепт + отчёт ОДНИМ прогоном
   argmax; `branch_recipe_dataframe`/Excel не сломаны — общая строка
   вынесена в `_recipe_row_dataframe`), `binding_report_dataframe`
   (тип veto|chance, % пула, значение в x*, порог, «выполнено в x*») и
   `binding_report_caption` с ТРЕМЯ состояниями: ✅ выполнено ·
   ⚠️ «оптимум НЕ НАЙДЕН» (допустимые точки в пуле есть — вопрос поиска) ·
   ⛔ «оптимум ЗАПРЕЩЁН» (100 % пула под биндингом — вопрос постановки,
   добор точек не поможет; CAMPAIGN_SPEC_PVC §7). Показ — сразу под
   рецептом ветки в рабочем столе.

### Роли узлов (9)

| `ABSOLUTE` | phr | `range`, `scale?` |

### Инварианты валидатора

1. k=2 → ровно один `SHARE_CLOSURE` + один `SHARE_FREE`.
2. k≥3 → все члены `SHARE_SIMPLEX`; `SHARE_CLOSURE` запрещён (C1:
   замыкание при k≥3 — внутреннее свойство сэмплера на `SimplexRegion`,
   не роль узла; группа даёт k−1 свободных координат; отдельные
   `min_share`/`max_share` не нужны).
3. `SHARE_CLOSURE` и `FIXED` — без `range`/`share_range`; наличие —
   ошибка валидации, не тихое игнорирование.
4. `group_order` — ТОЧНАЯ перестановка множества групп с ролью
   `GROUP_TOTAL` (C2). `GROUP_TOTAL_FIXED` (RESIN) исключается: тотал
   детерминирован, стратифицировать нечего. Несовпадение множеств —
   ошибка (не «лишние игнорируются»).
5. `min_phr`/`max_phr` разрешены на любом share-узле, задаются в phr,
   в ядре превращаются в conditional narrowing (не box).
6. Share-бокс группы (C5, вместо per-node range):
   `Σφᴸ ≤ 1 ≤ Σφᵁ` и `φᵢᵁ ≤ 1 − Σ_{j≠i} φⱼᴸ ∀i` — сравнения
   **нестрогие** (LUB впритык: 0,60 = 1 − 0,40; строгое `<` даст ложный
   отказ). Для k=2 диапазон closure — производный
   `[1−φᵁ_free, 1−φᴸ_free]`, он вычисляется, не задаётся.

### Что зафиксировано реализацией B1 (iter45, `src/design/phr_sampler.py`)

Тесты: `tests/unit/test_iteration45_phr_min_max.py` (13 шт.); регресс
iter34/35/37/38/39/40/41/9 — 162 зелёных.

1. `min_phr`/`max_phr` допустимы **только на `share_of`**-узлах: у
   `absolute`/`ratio_to` границы уже заданы в собственных координатах,
   дублирующий лимит в phr там был бы вторым источником истины.
2. Публичный `PhrSpec.share_bounds_at_total(parent, T)` — эффективные
   границы долей с учётом лимитов узла И партнёров по группе
   (`loᵢ = max(lo₀ᵢ, 1 − Σ_{j≠i} hi₀ⱼ)`). Партнёрское сужение работает и
   СНИЗУ: при T=15 `lo_CPE = 1 − 8/15 = 0,4667`, а не `φᴸ = 0,30` —
   потолок партнёра поднимает чужой пол.
3. **Окно тотала.** Лимиты в phr ограничивают не только долю, но и сам
   тотал: `T ≥ min_phr/φᵁ`, `T ≤ max_phr/φᴸ`, плюс `Σlo₀(T) ≤ 1 ≤ Σhi₀(T)`
   (обе суммы невозрастают по T ⇒ бисекция даёт интервал). Окно применяется
   к `sample_z`/`clip_z`/`z_bounds`/`encode` и к `phr_intervals()`.
4. **Сужать можно только `absolute`-ось без cap.** Если окно у́же
   заявленного интервала, а тотал задан `ratio_to`/`share_of`/`absolute+cap`,
   пришлось бы сужать пер-точечно вверх по DAG — не реализовано, поэтому
   явная ошибка конфига вместо тихого приближения (A0.6).
5. **Диагностика от частного к общему**: сначала «узел X: лимиты не
   пересекаются с достижимым диапазоном», затем групповые сообщения. Для
   `fixed`-тотала пер-узловая проверка и окно эквивалентны (`t_lo == t_hi`),
   поэтому отдельной fixed-ветки нет — она была бы мёртвым кодом.
6. Лимиты входят в `to_dicts()`/`spec_hash()`, но **только когда заданы** —
   спеки без лимитов сериализуются как до iter45, хеши iter35/36 не «уехали»
   (`44f0f96a…` для `_phr_spec_pvc.json` остаётся валиден до B2).
7. `encode` отвергает рецепт вне лимитов (ошибка данных), `quantize_recipe`
   добавляет лимиты в `violations` как страховку (обычно перекрывается уже
   суженным `phr_intervals`).

### Что зафиксировано реализацией P3.3 (iter57, 08.08.2026)

Тесты: `tests/unit/test_iteration57_linked_axes.py` (46 шт.); регресс

1. **Связка — ПОЛИТИКА кампании, не схема** (канон уровней iter51):
   `runner.process_links` (`ProcessLink: name = minuend − subtrahend ∈
   [lo, hi]`, физические единицы; `None` у границы — односторонняя полоса,
   в JSON пишется `null`, не `Infinity`). Валидация `normalize_links`
   (A0.6, явные отказы): имена против ПОЛНОГО process-блока; имя связки не
   совпадает с осью; уменьшаемое ≠ вычитаемое; **ось не более чем в ОДНОЙ
   связке** (последовательная проекция двух полос с общей осью не
   гарантирует совместного решения); lo < hi, хотя бы одна сторона
   конечна; полоса обязана пересекать достижимый диапазон разности
   `[aL−bU, aU−bL]` — иначе область пуста, проекция не определена.
2. **Слой = ПРОЕКЦИЯ на полосу** (`design/linked_axes.py`,
   `snap_pair_to_band`): минимальный L2-сдвиг пары в ФИЗИЧЕСКИХ единицах
   (в коде [0,1] оси с разным размахом весились бы по-разному) на грань
   `a−b = hi|lo` — симметричный `∓Δ/2`, затем clip к отрезку грани внутри
   боксов (непустота гарантирована статической валидацией).
   Идемпотентна; входы не мутируются. Проекция — ПОСЛЕ розыгрыша Соболя
   (bit-в-бит тест: смесь и несвязанные оси не тронуты — тот же аргумент,
   что у уровней).
3. **Ось не может одновременно нести уровни и связку** — явная ошибка в
   ОБОИХ сеттерах (`set_process_levels` ↔ `set_process_links`):
   последовательные проекции ломали бы друг друга, «почти на уровне /
   почти в полосе» — тихая ложь. Уровни на СВОБОДНОЙ оси (rpm) законно
   сосуществуют со связкой темповых осей (тест).

## iter82. Цены сырья правятся НА ЖИВОМ проекте (продолжение iter75)

**Наблюдение сессии 12.08.2026 (вопрос технолога «можем добавить цены на
сырьё после старта проекта?»).** Ядро это умело всегда, UI — нет:

* `MixtureProcessRunner.set_project_economics` (iter75) — обычный сеттер,
  базу опытов, схему и `spec_hash` не трогает; сценарий «цены на уже
  измеренной базе» покрыт тестами iter75;
* но в интерфейсе цены жили ТОЛЬКО в форме «🆕 Новый проект», а её кнопка
  `setup_build` зовёт `build_setup_runner` — новый раннер с **пустой
  базой**. То есть смена закупочной цены стоила всех измеренных опытов;
* вторая мина: ветка наследует проектные цены ОДИН РАЗ, при рождении
  (`create_branch` кладёт замыкание `linear_price_fn` в `_branch_cost`) —
  это **снимок**. После правки цен старые ветки продолжали считать по
  старым, и увидеть это было негде.

**Файлы:** `src/apps/campaign.py` (`branch_price_vector`,
`project_economics_report`, `CampaignController.economics_report` /
`set_project_prices`), `src/apps/campaign_ui.py`
(`project_economics_dataframe`, `branch_prices_dataframe`,
`price_edit_message`, `render_project_economics` — подключён в
`render_project_settings`). Тест: `test_iteration82_project_prices_edit.py`
(28 passed).

### Принятые решения

1. **Правка цен — операция ЖИВОГО проекта, а не пересборки.**
   `set_project_prices` делегирует в штатный `set_project_economics` (вся
   валидация там: ρ среди откликов, полнота цен, знак) и меняет ТОЛЬКО
   `component_prices`; ρ, единицы и роль ρ по умолчанию сохраняются.
   Инвариант И-1 проверяется `assert`: `len(runner.points)` не меняется.
2. **Перенос цен на существующие ветки — ЯВНЫЙ (A0.6).** По умолчанию
   `apply_to_branches=False`: ценовая нога ветки — часть её истории, менять
   её задним числом молча нельзя. Новые цены подхватывают только ветки,
   рождённые ПОСЛЕ правки; расхождение помечается флагом `stale` и
   предупреждением в панели. С галочкой ветки переводятся на текущие цены
   (перезапись `_branch_cost`) и их `d_best` пересчитывается — измеренные
   отклики при этом не меняются.
3. **Undo-стек ЗАПЕЧАТЫВАЕТСЯ.** Снимки undo несут СТАРУЮ ценовую ногу:
   оставленный стек вернул бы её вместе с откатом роли — скрытая потеря
   новой цены. Это правка ФАКТА проекта, а не обратимой интерпретации
   ветки (§7 — про интерпретацию), поэтому стек обнуляется.
4. **«Не знаю» вместо выдуманных нулей.** `branch_price_vector` читает
   цены из сериализуемого дескриптора `price_spec`; нелинейная/непрозрачная
   функция цены ⇒ `None`, `stale=False` (сравнивать нечего), в таблице —
   «не линейная (не читается)».
5. **Экономика видна в «📋 Настройки проекта».** До iter82 после загрузки
   проекта цены не показывались нигде — панель читает движок
   (`project_economics_report`), а не поля формы. Отдельно репортится
   «включено, но все цены нулевые» (себестоимость тождественно нулевая).
6. **Отказ, если экономика не настроена.** Нет ρ — цены прикладывать
   некуда: явный `ValueError`, а не тихое включение экономики «за
   пользователя». Объявить ρ на непустой базе нельзя без
   `add_response` (у снятых точек `Y[ρ]=MISSING`, плотность придётся
   домерить) — это осознанно оставлено пересборке/эволюции схемы.

### Замечание про панель и закладки (наблюдение UI-теста)

## iter83. Достижимость ОТВЕСА от ВЕСА ЗАМЕСА (замена «г на 1 phr») — ✅ СДЕЛАНО

**Файлы:** `src/apps/campaign_ui.py` (хелперы + поле формы + проверка при
сборке), `src/design/project_package.py` (проекция паспорта пакета),
`tests/unit/test_iteration83_batch_weighing.py` (38 тестов; регресс по
iter42/54/71/72/73/76/81/82 — 326).

### Отказ, зафиксированный в живой сессии (12.08.2026)

Паспорт кампании просил **«г на 1 phr»** — величину, которой в цехе не
оперируют. Формулировка технолога: *«чтобы указать этот показатель, нужно
предварительно посмотреть различные варианты рецептов и условно выбрать тот,
где на 100 частей смолы у него максимальный или желаемый ввод массы этого
компонента, но реально так никто не делает»*. Прикладной вопрос звучит иначе:
**замес N кг, весы с такой ценой деления — возьмётся ли навеска, где нужен
премикс**.

Маршрут, которым думает технолог (и которым теперь считает UI): массовые части
→ массовые **доли** → граммы через вес замеса → сравнение с разрешающей
способностью весов.

### Что зафиксировано реализацией

1. **`batch_sigma_phr(spec)`** — Σphr по **листьям** (`component_names`), не по
   всем узлам `phr_intervals()`: узел-тотал группы = сумма детей, сложение всех
   узлов подряд считает группы дважды. Golden на референсной спеке:
   `109.85 … 147.80`; сумма всех узлов даёт `114.85 … 162.80` — завышение верха
   ровно на тотал `SOFT`. ⚠️ Эта ошибка ЖИЛА в
   `assistant/tools/readonly.get_spec.sigma_phr_static` — именно оттуда шли Σphr,
   которые ассистент цитировал в ПВХ-сессии. **ИСПРАВЛЕНО в iter84 п.1:** сумма
   переехала в ядро (`PhrSpec.sigma_phr_bounds`), своих копий арифметики у слоёв
   больше нет.
2. **`batch_grams_per_phr(spec, batch_kg)`** — перевод «вес замеса → масштаб
   ядра» по **верху** Σphr: `г/phr = кг · 1000 / Σphr_max`. Верх выбран
   осознанно: Σphr от рецепта к рецепту плавает, а масштаб ядра обязан быть
   ОДИН; верх даёт наименьший `г/phr` ⇒ наибольшую `δ_phr` ⇒ осторожную оценку
   разрешения. Занижать δ опаснее — это молча обещало бы точность, которой нет.
3. **`batch_weighing_report(spec, batch_kg, step_g, min_steps=20)`** — таблица
   достижимости: доля L/U · навеска min (г) · шагов весов · погрешность (%) ·
   phr lo/hi · вердикт. Навеска считается **через доли** (`fraction_bounds`), и
   это НЕ то же самое, что через `г/phr`: для fixed-узлов совпадает точно
   (`RESIN` 16914.75 г), для варьируемых расходится (`DINP` 725.69 против
   676.59 г), потому что Σphr_max недостижим — у групп Σφ = 1, у capped-осей
   работает потолок. Поэтому оценивать навеску через `г/phr` нельзя.
4. **Бокс консервативен в БЕЗОПАСНУЮ сторону.** `fraction_bounds` содержит
   образ decode, значит расчётная навеска ≤ фактической (проверено
   сэмплированием 800 точек: `DINP` фактический минимум 805.77 г против
   расчётных 725.69 г). Хелпер может перестраховаться, но не пропустит
   невзвешиваемый компонент.
5. **Вердикты**: `невозможно` (навеска < цены деления) · `грубо`
   (< `min_steps` шагов, т.е. погрешность ≥ 5%) · `премикс`
   (`premix_required` — правило ядра iter35, не своя копия) · `низ 0` ·
   `ок`. Порог 20 шагов — та же 5%-я планка, что у премикса, но в другой
   проекции: премикс смотрит на РАБОЧИЙ ДИАПАЗОН оси, а «грубо» — на саму
   НАВЕСКУ (ось может быть широкой, а нижняя доза мизерной — это разные
   отказы). `низ 0` — отдельная метка, а не «невозможно»: компонент МОЖЕТ
   отсутствовать, отвес по нулю не нормируется, и тревога была бы ложной.
6. **Поле формы**: «г на 1 phr (паспорт)» → **«Вес одного замеса рецепта, кг
   (паспорт)»**; «Шаг весов, г» → «Цена деления весов, г». Ключ
   `setup_pass_weigh_gpp` СОХРАНЁН (переименование сломало бы сохранённые
   проекты и барьер `SETUP_UNSETTABLE_*`), но **семантика значения сменилась:
   в нём кг, а не г/phr**. В ядро (`set_weighing_resolution`) по-прежнему уходит
   `г/phr` — считается автоматически, человек его не вводит.
7. **Проверка при сборке проекта**: после `set_phr_spec` кнопка
   «🏗 Построить проект» показывает подпись + экспандер с таблицей
   (`st.warning`, если есть проблемы; экспандер раскрыт). Сборка **не
   блокируется** (A0.6) — решение (премикс, другой замес, другие весы) за
   технологом. Вес замеса БЕЗ активной спеки — явный `ValueError`: Σphr
   неизвестна, переводить нечем (молчаливый пропуск половины паспорта
   недопустим).
8. **Обратный перевод `batch_kg_from_grams_per_phr`** — точное обращение п.2
   для префилла формы (`setup_prefill_from_runner`,
   `package_to_setup_prefill`): круг «собрать → загрузить → собрать» не сдвигает
   паспорт (проверено на 0.5/1/25/300 кг). Без спеки / на мусорном масштабе —
   `0.0` («не задано»), а не правдоподобная выдумка.
9. **ОСОЗНАННАЯ смена контракта двух существующих тестов** (как в iter52):
   `test_iteration54::test_prefill_contains_passport_keys` теперь ждёт `0.0`
   (у раннера фикстуры нет спеки ⇒ перевод невозможен; сам паспорт в ядре НЕ

### 4. Вес запроса: −31 % на ход

Замер живой ПВХ-сессии: 43 реплики, 100 862 символа ≈ 25 215 токенов при
бюджете 24 000 — то есть бюджет НЕ СРАБАТЫВАЛ никогда, и каждый вопрос тащил к
модели весь разговор. Полный запрос: system 19 851 + user 8 675 +
assistant 73 987 символов + JSON-схемы 26 инструментов 16 592 = **29 776
токенов на ход**.

Два рычага:

1. **Вырезание устаревших разделов `## ЧИСЛА`** из ПРОШЛЫХ ответов
   (`strip_numbers_section`). Это снимок показаний инструментов на момент того
   хода: он и объёмный (21 520 символов у ответов сессии), и скоропортящийся —
   спека между ходами меняется, а канон промпта требует брать геометрию вызовом
   инструмента. Раздел ПОСЛЕДНЕГО ответа сохраняется: на его числа опирается
   уточняющий вопрос. Вместо тела — короткая пометка (A0.6: пустой заголовок
   модель прочитала бы как «инструменты ничего не вернули»).
2. **`CONTEXT_TOKENS` 24 000 → 12 000** — примерно 15–20 последних реплик:
   рабочая ветка цела, отсечённое помечено `[сессия]` и лежит в `session.json`.

Итог замера: **29 776 → 20 426 токенов (−31,4 %)**, в модель уходит 22 реплики
из 43. Обрезка касается ТОЛЬКО сборки запроса — сессия, файл проекта и показ на
экране полные (тест `test_session_and_disk_not_mutated`).

**Инвариант, найденный тестом:** замена НЕ ДОЛЖНА удлинять текст. Первая
реализация имела подробную пометку, и на коротком разделе она оказывалась
длиннее вырезанного тела — «оптимизация» раздувала запрос тем сильнее, чем
лаконичнее отвечала модель. Теперь пометка короткая, а `strip_numbers_section`
возвращает исходный текст, если замена не дала выигрыша.

### 5. Стоимость хода стала видимой

`views.context_caption` говорил только «43 из 43», и это читалось как «всё в
порядке», хотя означало «уходит весь разговор». Теперь подпись называет объём
переписки в токенах и экономию от обрезки, а бюджет берёт ФАКТИЧЕСКИЙ
(`CONTEXT_TOKENS`): свой дефолт был бы вторым источником истины — подпись
показывала бы 24 000, пока ход считает по 12 000.

### Что осталось хвостом

* каталог инструментов уходит ДВАЖДЫ: текстом в системном промпте
  (`tool_catalog`, 8 721 символ) и JSON-схемами в поле `tools` (16 592 символа) —
  это ~6 тыс. токенов на каждый ход. Текстовый каталог держится контрактом
  iter64 (`test_new_tool_appears_without_editing_prompt`: новый инструмент обязан
  появляться в промпте без ручной правки), поэтому сокращение — отдельный шаг с
  переписыванием того теста, а не правка «на ходу»;
* раздел `## OPEN_QUESTIONS` в истории — 25 560 символов у ответов ПВХ-сессии,
  БОЛЬШЕ, чем `ЧИСЛА`. Он тоже частично устаревает (вопрос уже закрыт решением),
  но в отличие от чисел это не снимок инструмента, а обязательство перед
  человеком: резать его без признака «отвечен» нельзя — потеряется то, о чём
  договорились спросить.

## iter85. Цены сырья вносятся ПОЗЖЕ сборки проекта — ✅ СДЕЛАНО

**Файлы:** `src/apps/mixture_process_runner.py` (`set_project_economics`,
`_set_component_prices`), `src/apps/campaign_ui.py` (`parse_component_prices`,
блок экономики формы сетапа, `render_project_economics`),
`tests/unit/test_iteration85_prices_deferred.py` (25 тестов; правка одного
теста iter75, регресс по iter20/21/25/72/73/74/75/76/81/82/83/84 — 362).

### Отказ, зафиксированный в живой сессии (13.08.2026)

Кнопка «🏗 Построить проект» отвечала: *«Нужно 18 цен компонентов ['PVC_67',
'PVC_71', … 'SA_1860'] через запятую (в том же порядке). Пустых значений быть не
может: нуль по умолчанию занизил бы себестоимость молча»* — и проект не
создавался. Формулировка технолога: цены мы договорились вносить в любой момент
до расчётов. Разбор нашёл ДВА независимых дефекта.

**1. Рассинхрон источника имён компонентов (баг).** Поле цен размечалось по
ТЕКСТОВОМУ полю «Компоненты смеси» (`mix_live`): и подпись, и дефолт
`"0, 0, 0"`. А гейт сборки требовал цены по `setup_mixture_names(mix, spec)`,
которая в режиме phr-спеки текстовое поле ИГНОРИРУЕТ и берёт
`spec.component_names` (iter41.1). С 18-компонентной спекой форма просила «3
цены», сборка требовала 18 — ввести правильное число было нельзя в принципе.

**2. Гейт цен на сборке противоречил iter82.** iter82 объявил правку цен
операцией ЖИВОГО проекта, но задать цены ВПЕРВЫЕ было негде: сборка без полного
набора отказывала, а панель «💰 Экономика проекта» при пустых ценах делала
`return` с текстом «задайте ρ и цены в форме "🆕 Новый проект"». Замкнутый круг,
причём цена приходит из снабжения позже, чем начинаются опыты.

### Принятые решения

1. **«ρ объявлена, цены НЕ заданы» — ЛЕГАЛЬНОЕ состояние.** `prices=None`/`{}`
   при `enabled=True` принимается ядром; полнота проверяется только у
   НЕПУСТОГО словаря. Пустой набор ≠ нули: `project_price_vector() == []` ⇒
   ценовой ноги нет вовсе (себестоимость не считается, ветки рождаются
   техническими), тогда как нуль означает «сырьё бесплатно» и в расчёт идёт.
   Занизить себестоимость тут нечему — её просто не начинают считать.
2. **Частичный список — по-прежнему отказ (A0.6).** Именно там недостающие цены
   доопределились бы нулём молча. Текст отказа теперь называет ЛЕГАЛЬНЫЙ выход
   («оставьте поле пустым»), а не только запрет: сообщение, которое запрещает,
   не показывая пути, читается как поломка.
3. **Дефолт поля — ПУСТО, а не «0, 0, 0».** Прежний дефолт был готовым
   заявлением «всё сырьё бесплатно» в одном клике от применения. Пустое поле
   сопровождается `st.info` — состояние видимое, а не тихое.
4. **Имена компонентов для цен — из ТОГО ЖЕ источника, что и сборка**
   (`setup_mixture_names`). Единый источник снимает дефект №1 целиком.
5. **Панель iter82 разделяет «нет ρ» и «нет цен».** ρ — измеряемый отклик, на
   снятых точках её пришлось бы домерять, поэтому объявление ρ осталось делом
   пересборки. Цены — факт снабжения: вводятся в панели в любой момент, включая
   первый раз. Поле при пустых ценах НЕ предзаполняется нулями — иначе один
   клик превратил бы «не знаю» в заниженную себестоимость.
6. **`all_zero` не маскирует «не знаю».** При пустых ценах отчёт даёт
   `all_zero=False` и `configured=False`: «цены не заданы» и «все цены нулевые»
   — разные диагнозы, и предупреждения у них разные.

### Третий дефект, найденный ПОСЛЕ первой правки (важно)

Пользователь сообщил, что отказ **воспроизводится и после исправления**, и
предположил, что нужен перезапуск приложения. Перезапуск был бы бесполезен:
значение приходило **с диска**. В `setup_draft.json` ПВХ-проекта лежало
`"setup_econ_prices": "0, 0, 0"` — записано прежним дефолтом, когда в составе
стояли шаблонные «A, B, C». Черновик возвращается в форму через
`setup_prefill_pending`, а Streamlit при УЖЕ существующем ключе виджета
игнорирует новый `value=""`. То есть новый пустой дефолт до поля не доходил, и
парсер честно видел 3 значения при 18 компонентах.

Общий урок: **значение поля переживает смену состава**, потому что живёт в
черновике на диске, а не в коде формы. Любое поле, чья ВАЛИДНОСТЬ зависит от
числа компонентов, обязано сверяться с текущим составом при применении
префилла.

Реализация — `campaign_ui.stale_prices_count` (чистая) + сверка в
`render_setup_form` ДО инстанцирования виджета:

* устаревшее значение **очищается**, и об этом говорит `st.warning` с числами
  («лежало 3 значения под прежний состав, компонентов сейчас 18») — молчаливая
  очистка была бы потерей пользовательского ввода без предупреждения;
* сверка применяется **только к значениям префилла** (`_pending`), а не к
  содержимому `session_state` вообще. Первая версия чистила любое несовпадение,
  и UI-тест `test_setup_still_refuses_partial_prices` немедленно поймал
  регресс: ручной ввод «95, 200» на трёх компонентах молча превращался бы в
  «цены не заданы» вместо явного отказа (A0.6);
* «0, 0, 0» при ТРЁХ компонентах устаревшим НЕ считается — это законное
  заявление «сырьё бесплатно» (о нём предупреждает отдельная проверка).

Проверено на фактическом черновике пользователя (18 компонентов, phr-спека):
поле очищается, предупреждение показывается, проект СОБИРАЕТСЯ,
`component_prices == {}`, `project_price_vector() == []`.
