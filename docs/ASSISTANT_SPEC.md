## Инварианты слоя (проверяются тестами)

1. **Сессия привязана к ПРОЕКТУ.** Живёт в
   `project_campaigns/<проект>/assistant/` — переезжает вместе с проектом при
   сохранении/загрузке/удалении. Смена проекта = смена сессии.
2. **Ни один write-инструмент не меняет состояние сам.** `propose_patch`
   только СТЕЙДЖИТ; `apply_patch` требует `human_token`, выданный кнопкой UI,
   и блокируется, если после патча падает `validate_spec` или гейт
   `preflight`.
3. **Тесты — контракт.** Песочница монтирует репозиторий только на чтение;
   правка `tests/` запрещена агенту вообще (защищённый набор — golden-числа
   iter45–57).
4. **Сети в песочнице нет.** Веб — отдельный канал (`:online`), не подпроцесс.
5. **`spec_hash` — единственный источник истины о геометрии.** Патч, который
   двигает отпечаток, помечается явно.
6. **L1 > L2 > L3.** Локальные факты технолога отменяют литературу; конфликт —
   СИГНАЛ в `OPEN_QUESTIONS`, не усреднение.
7. **Полный лог вызовов** пишется в артефакт кампании (`tool_calls.jsonl`) —
   разбор воспроизводим.
8. **Усечение контекста НЕ теряет историю**: в модель уходит хвост диалога,
   на диске остаётся всё, факт усечения виден в контексте явной пометкой.

## §8. Golden-сценарии маршрутизации (контракт «вопрос → чем отвечаем»)

Восемь типовых обращений технолога. Для каждого зафиксировано, КАКИМИ
инструментами архитектор обязан его закрывать (без них ответ — работа по
памяти) и чего в этом сценарии быть не должно. Таблица живёт в коде
(`prompts.GOLDEN_SCENARIOS`), промпт получает её словами, тест сверяет с ней
маршрут — три представления одного контракта.

| # | Ключ | Вопрос технолога | Инструменты | Почему так |
|---|---|---|---|---|
| 1 | `explain_bounds` | «Почему диапазон не такой, как я вводил» | `explain_node` | эффективная граница СЧИТАЕТСЯ ядром (техлимит партнёра, закрытие группы), а не пересказывается по вводу |
| 2 | `wedge_refusal` | «Привяжи УФ жёстко к пластификатору» | `simulate_bounds` | клин `RATIO_TO` вшивает монотонный prior: corr 0.89 против 0.14 у трапеции — возражаем ЧИСЛАМИ |
| 3 | `l1_widen` | «В цехе льём DINP до 20 phr» | `explain_node` → `validate_spec` → `propose_patch` | L1 отменяет договорённость: dry-run → патч в СТЕЙДЖ (CONVENTIONAL/L1) + пометка сдвига `spec_hash` |
| 4 | `attachment` | «Приложил паспорт TiO2 — что взять в спеку» | `list_attachments`, `read_attachment`, `get_local_facts` | читаем ДОКУМЕНТ, а не имя файла; конфликт с L1 — в `OPEN_QUESTIONS`, характеристики не выдумываем |
| 5 | `whatif` | «Что изменится, если сузить SOFT до 5–10» | `validate_spec`, `simulate_bounds` | это ВОПРОС, а не поручение: dry-run без записи, `propose_patch` здесь запрещён |
| 6 | `sandbox` | «Прогони тесты — не сломает ли правка golden» | `run_pytest` | проверка исполнением; сети нет, запись в репозиторий и правка `tests/` запрещены |
| 7 | `handoff` | «Примени сам и запиши решение» | — (кнопка человека) | класс `write` модели не выдан по построению: объясняем, где кнопка и что она сделает |
| 8 | `status` | «Можно строить план? почему preflight ругается» | `preflight`, `campaign_overview` | состояние берётся из движка; проект не собран ⇒ «не проверено», а не «всё хорошо» |

Во ВСЕХ восьми запрещены `apply_patch` / `reject_patch` / `record_decision` /
`add_local_fact` — это ровно класс `write` реестра (список в коде не выдуман, а
сверяется с реестром тестом).

## Что зафиксировано реализацией iter58 (08.08.2026)

Тесты: `tests/unit/test_iteration58_assistant_session.py`; демо:
`.venv\Scripts\python.exe run_assistant_demo.py`.

1. **Сессия — JSON-native dataclass-контейнер** (`session.py`), без numpy и без
   Streamlit: `Message` / `Attachment` / `Artifact` / `StagedPatch` /
   `ToolCall`. Один формат (`assistant-v1`) читается и пишется
   `to_state`/`from_state` — round-trip побайтно стабилен.
2. **Привязка к проекту — через КАТАЛОГ, а не поле в `campaign.json`**:
   сессия лежит рядом (`assistant/session.json`), поэтому
   `save_campaign`/`load_campaign` не трогаются, а `delete_campaign` (rmtree
   каталога проекта) уносит и переписку — отдельной синхронизации нет.
   Загрузка несуществующей сессии — ПУСТАЯ сессия проекта, не исключение
   (старые проекты грузятся без ошибок, как `sampling_groups` iter31).
3. **Усечение контекста (`context_messages`) НЕ теряет историю**: в модель
   уходит хвост, помещающийся в бюджет, а вместо отрезанного — ОДНО явное
   системное сообщение «опущено N ранних сообщений (полный лог в
   session.json)». Молча урезанный диалог выглядел бы как амнезия ассистента.
4. **Staged-патч несёт поля формата ответа архитектора** (`node`, `field`,
   `from`/`to`, `bound_type` PHYSICAL|CONVENTIONAL, `level` L1|L2|L3,
   `source`, `rationale`, `confidence`, `affects_hash`) — таблица патчей в UI
   собирается без домысливания. Статусы: `staged` → `applied` | `rejected`;
   переход из терминального статуса — явная ошибка.
5. **Дедуп вложений по sha256**: повторное приложение того же файла
   возвращает СУЩЕСТВУЮЩУЮ запись (одно имя — один экземпляр на диске), а не
   плодит копии в контексте.
6. **Журналы — append-only jsonl** (`tool_calls` / `decision_log` /
   `local_facts`): дописывание не переписывает файл целиком, битая строка при
   чтении пропускается с пометкой, а не роняет загрузку проекта.
7. **`views.py` — ОДИН источник таблиц**: демо-скрипт и будущий док печатают
   один и тот же `messages_dataframe` / `attachments_dataframe` /
   `staged_patches_dataframe` / `artifacts_dataframe` / `tool_calls_dataframe`
   и подпись `session_caption`. Разъехавшиеся представления врали бы
   пользователю про одно и то же состояние.

## Что зафиксировано реализацией iter59 (08.08.2026)

Тесты: `tests/unit/test_iteration59_assistant_files.py` (25 шт.); регресс
iter58 — 39; демо: раздел «iter59 · ФАЙЛЫ В СЕССИИ».

1. **Читаем 7 семейств форматов**: текстовые (txt/md/csv/tsv/log/…), json
   (разворачивается с отступами — так модель видит структуру), xlsx/xlsm
   (лист за листом, ячейки табуляцией), docx (абзацы + таблицы), pdf
   (постранично, `pypdf` добавлен в `requirements.txt`). Всё прочее — ЯВНЫЙ
   отказ со списком принимаемых расширений: тихо приложенный бинарник
   превратился бы в мусор в контексте.
2. **PDF-скан без текстового слоя объясняет себя**: текст пуст, но `note`
   говорит «текстового слоя нет (похоже на скан) — нужен OCR». Это прямое
   следствие запрета выдумывать данные паспортов: молча пустое вложение
   читалось бы моделью как «в паспорте этих характеристик нет», и запрет
   работал бы против пользователя.
3. **Дедуп по содержимому, а не по имени**: тот же файл под именем
   «(копия)» возвращает СУЩЕСТВУЮЩУЮ запись и не пишет второй экземпляр на
   диск (демо печатает «записей было 3, стало 3»).
4. **Дайджест vs полный текст**: в контекст идёт `attachment_digest`
   (имя/тип/размер + начало текста), полный — только по запросу
   `attachment_text(start, length)` с флагом `has_more`; при усечении хвост
   ДОЧИТЫВАЕТСЯ с диска, а не теряется.
5. **Кодировки цеха**: utf-8 → cp1251 → utf-8 с заменой. Выгрузки из
   лаборатории часто в cp1251, и «кракозябры» в паспорте — та же потеря
   данных, только незаметная.
6. **Отказ не оставляет мусора**: если извлечение не удалось, файл на диск НЕ
   пишется и записи в сессии не появляется (тест) — иначе в проекте копились
   бы «половинчатые» вложения.
7. **Файлы-сироты показываются, а не удаляются** (`orphan_files`): документ
   мог остаться от очищенной переписки и всё ещё быть нужен.

## Что зафиксировано реализацией iter60 (08.08.2026)

Тесты: `tests/unit/test_iteration60_assistant_llm.py` (20 шт., сеть НЕ нужна —
транспорт подменяется); демо: раздел «iter60 · ХОД АССИСТЕНТА».

1. **Конфиг вынесен из UI** в `assistant/config.py` (ключ, модель, локальный
   `.env`): движок ассистента, инструменты и будущий MCP-сервер не должны
   зависеть от Streamlit-модуля, а ключ — читаться двумя способами. Дефолтная
   модель — `anthropic/claude-sonnet-4.5`.
2. **`:online` — ТУМБЛЕР, а не другая модель** (`online_model`): суффикс
   приписывается ровно один раз и снимается при выключении. Факт веба
   помечается в сообщении сессии (`Message.web`) — иначе утверждение из сети
   неотличимо от утверждения из контекста проекта, а это разные уровни знания
   (L2 против L1/L3).
3. **Цикл `run_tool_loop`**: модель → инструменты → модель, пока не появится
   ответ без вызовов. Возвращает `new_messages` В ПОРЯДКЕ появления (включая
   роль `tool`) — их дописывают в сессию целиком, иначе следующий вопрос
   потеряет контекст уже сделанных вызовов.
4. **Ошибка инструмента уходит МОДЕЛИ** как результат (`ОШИБКА ИНСТРУМЕНТА …`),
   а не рушит ход: отказ `validate_spec` на неверной роли узла — это ПОЛЕЗНЫЙ
   сигнал, из которого модель делает вывод; пользователю нужен разбор, а не
   стектрейс. Битые аргументы (не JSON) обрабатываются так же.
5. **Лимиты объявляются**: `max_iterations` (по умолчанию 8) и общий
   `time_budget_s` (180 с). При исчерпании — честный текст «предел вызовов» /
   «бюджет времени исчерпан», а не молчаливая обрезка. Результат инструмента
   длиннее `MAX_TOOL_RESULT_CHARS` усекается С ПОМЕТКОЙ.
6. **Прогресс наружу** (`on_event` + `progress_caption`): события
   `llm_request` / `tool_start` / `tool_end` / `done` с длительностью. Это
   прямое требование к UI — долгий `run_pytest` не должен выглядеть зависанием;
   сбой обработчика событий не роняет ход (обёрнут).
7. **Транспорт подменяем** (`transport=`) — тесты и демо гоняют весь цикл БЕЗ
   сети; HTTP-ошибки переводятся в человеческие подсказки (401 — ключ, 402 —
   баланс, 404 — имя модели, 429 — частота).

   `sandbox` недоступны из readonly-режима, даже если модель узнала имя
   функции из истории (тест с `dummy_write_tool`). Запрет, живущий только в
   тексте промпта, снимается одной удачной формулировкой пользователя.
4. **Golden-числа, а не «вернулся словарь»**: `explain_node('PBNK')`
   воспроизводит немонотонную `hi_φ(T) = min(0.70, 8/T, 1−3/T)` — 0.40 @T=5,
   полка 0.70 @T=10.5, 0.5333 @T=15 (iter45/B1). Потолок ПАРТНЁРА поднимает
   чужой пол: `lo_CPE(15) = 1 − 8/15`. Ответ на «почему диапазон не такой, как
   я ввёл» теперь считается, а не пересказывается.
5. **`simulate_bounds` отличает КЛИН от ТРАПЕЦИИ числами**: corr(UV, DINP)
   = 0.14 при `ABSOLUTE_CAPPED` против 0.89 после патча в `RATIO_TO`. Это
   рабочий аргумент отказа на «привяжи УФ к пластификатору»: клин вшивает
   монотонный prior, который данные уже не опровергнут.
6. **Патч — только dry-run.** `validate_spec` применяет патч к КОПИИ
   (`apply_patch_to_dicts` + конструктор), отдаёт дифф границ и объявляет сдвиг
   `spec_hash`; спека проекта не меняется (тест сверяет hash до/после).
   Отклонение валидацией — это `ok=False` с текстом ошибки, а НЕ исключение:
   для архитектора «так нельзя, потому что…» — ответ по существу.
7. **`normalize_patch` принимает все формы, которые естественно порождает
   модель** (`{node, field, value}`, `{node, set, unset}`, `{"UV": {...}}`,
   списки; спека целиком — узел `__spec__`). Добавление/удаление узлов патчем
   ЗАПРЕЩЕНО с объяснением: это смена схемы проекта, а не правка границы.
8. **`point_report` отдаёт и координату, и phr** (`coord` + `phr`): у
   share-узлов граница живёт в ДОЛЯХ, и сравнение «0.533 против 8» выглядело бы
   нарушением там, где его нет. Активное ограничение помечено явно
   (`active_hi = "max_phr"` — давит складской лимит, а не `share_range`).
9. **Отказы — содержательный текст, уходящий МОДЕЛИ** (A0.6): нет узла — со
   списком имеющихся; нет проекта/спеки — с указанием, где их собрать; вне
   геометрии `encode_recipe` — «признать anchor непредставимым, молча подгонять
   нельзя». Аудит (`dispatcher(on_call=…)`) пишется и на успехе, и на отказе.
10. **`long_running` объявлен в реестре** (`simulate_bounds`, `preflight`) —
      UI берёт признак прогресс-бара из данных, а не из зашитого списка имён.

## Что зафиксировано реализацией iter63 (09.08.2026)

Тесты: `tests/unit/test_iteration63_assistant_write.py` (45 шт.); регресс
iter58–62 — 178; демо: раздел «iter63 · WRITE-ИНСТРУМЕНТЫ».

1. **Появился класс доступа `propose`** между `readonly` и `write`. Граница
   проведена не по «опасности операции», а по вопросу «кто автор изменения»:
   `propose_patch` кладёт патч в СТЕЙДЖ сессии (обратимо, состояние проекта не
   трогается) и потому доступен модели; `write` — акт человека. Модели
   выдаётся `AGENT_KINDS = (readonly, propose, sandbox)`, и `apply_patch` для
   неё недостижим ПО ПОСТРОЕНИЮ, а не по тексту промпта.
2. **Подтверждение — разовый токен** (`consent.py`), а не флаг «пользователь
   согласен»: одноразовый, привязан к ДЕЙСТВИЮ, к ЦЕЛИ (id патча) и к
   `spec_hash` на момент нажатия кнопки, со сроком жизни. Отсюда четыре
   закрытых дыры: применить дважды, применить «не тот» патч, воспользоваться
   токеном из переписки и — главное — применить патч, посчитанный от УЖЕ
   УСТАРЕВШЕЙ геометрии (между кнопкой и вызовом спеку успели поменять).
3. **Патч, не прошедший dry-run, в стейдж НЕ попадает.** Иначе в панели
   копились бы заведомо неприменимые пункты, и разбор «почему не применяется»
   перекладывался бы на человека. Отказ возвращается модели текстом, чтобы она
   исправила патч сама.
4. **Три гейта применения, и каждый называет причину**: (а) валидация
   конструктора; (б) УЖЕ ИЗМЕРЕННЫЕ точки — если после патча опыт выпадает из
   геометрии (тест: сужение DINP до 8 phr выбрасывает точку с 13 phr), это
   молчаливое обесценивание части базы; (в) preflight — блокируем ТОЛЬКО
   ухудшение (гейты проходили → перестали): красный preflight до патча
   запрещал бы вообще любые правки. Заблокированный патч остаётся в стейдже.
5. **Не проверено ≠ пройдено**: без собранного проекта гейты возвращают
   `checked=False` с причиной («база точек пуста», «preflight не с чем
   сравнивать»), а не молчаливое «ok». Разница между «проверили и хорошо» и
   «проверить было нечем» — это разница в доверии к решению.
6. **Отказ фиксируется наравне с применением.** `reject_patch` пишет в
   `decision_log.jsonl` такую же запись, как `apply_patch`: через полгода спор
   «почему тогда не расширили границу» разрешает журнал, а не память
   участников. В записи всегда есть `spec_hash` (и `spec_hash_after` у
   применения) — иначе решение невозможно сопоставить с геометрией.
7. **L1-факты и ADR пишет ЧЕЛОВЕК** (`add_local_fact`, `record_decision` —
   класс `write` с токеном): модель может только предложить формулировку.
   Факт, записанный моделью в журнал высшего уровня знания, отменял бы
   литературу от своего имени.
8. **Ничего не теряется молча и без проекта**: если `root/project` не заданы,
   запись возвращается с `persisted=False` и пояснением, а не исчезает.
   `apply_patch` меняет спеку в ПАМЯТИ проекта и явно говорит `persist_hint`
   («сохраните кампанию»), а также предупреждает о сдвиге `spec_hash`.
9. **Показ — те же чистые хелперы**: `consents_dataframe` (на что человек
   нажал кнопку и до когда) и `apply_result_caption` (что поехало, сколько
   точек проверено, ухудшился ли preflight) используются и демо, и будущим
   доком.

## Что зафиксировано реализацией iter64 (09.08.2026)

Тесты: `tests/unit/test_iteration64_assistant_prompts.py` (53 шт.); регресс
iter58–63 — 223; демо: раздел «iter64 · ПРОМПТ АРХИТЕКТОРА И МАРШРУТИЗАЦИЯ».

1. **Промпт — рабочая ИНСТРУКЦИЯ, а не «характер» помощника**, и потому
   проверяется тестом: роль архитектора («числами из ядра»), иерархия знания,
   границы, формат ответа и табличка маршрутизации собираются блоками

   `routing_block`) в `architect_system_prompt(...)` под текущее состояние
   сессии (~9.8 тыс. символов, ≈2.4 тыс. токенов).
2. **Каталог инструментов ГЕНЕРИРУЕТСЯ из реестра** (`tool_catalog`), а не
   переписан руками: список в промпте разъезжается с кодом на первой же
   итерации, и модель начинает звать то, чего нет (тест добавляет
   `dummy_probe_tool` и видит его в промпте без правки текста). Класс `write`
   в каталог не попадает ВООБЩЕ — промпт не должен даже намекать, что
   применение доступно модели (iter63).
3. **Контекст сессии говорит правду о состоянии**: не собранный проект назван

   про уровень L2, число вложений — про `read_attachment` вместо пересказа по
   имени файла.
4. **Роутер `route()` — ЧИСТАЯ детерминированная функция**. «Ассистент
   отвечает правильно» нельзя закрыть тестом, который ходит в сеть, — а вот
   «правильно ли выбран путь» можно. Все 8 golden-сценариев §8 попадают каждый
   в свой вид и ровно в свой набор инструментов (параметризованный тест
   сверяет маршрут с `GOLDEN_SCENARIOS`).
5. **Порядок правил ЗНАЧИМ и обоснован смыслом, а не удобством разбора**:

   инструментов нет), а «что изменится, если сузить…» перебивает «сузь…»

   пограничные формулировки рядом.
6. **Непонятный вопрос — `clarify`, а не случайный инструмент.** Угаданный
   маршрут дороже честного «уточните»: ответ по неверному инструменту выглядит

7. **`HUMAN_ONLY` не выдуман, а сверяется с реестром** (`tool_names([WRITE])`):
   запрещённое во всех восьми сценариях — ровно класс `write`. Появится новый

8. **`check_routing` возвращает РАЗБОР, а не голый `bool`**, и различает два

9. **Запрет держится ДИСПЕТЧЕРОМ, а не текстом промпта**: в тесте модель всё

   падает (A0.6) и заканчивается объяснением, где кнопка. Запрет, живущий
   только в промпте, снимается одной удачной формулировкой пользователя.
10. **`with_system` держит РОВНО ОДИН** системный промпт архитектора
    (метка `PROMPT_MARK`): приклеенный вторично он удваивал бы инструкции и
    съедал бюджет контекста. Служебные пометки сессии (усечение истории,

11. **Ответ разбирается на секции** (`parse_sections` / `missing_sections`):

    — вопросы к человеку. Пустой раздел отбрасывается: «OPEN_QUESTIONS» без

12. **Показ — те же чистые хелперы**: `scenarios_dataframe` (контракт §8) и
    `routing_dataframe` (итог сверки хода) используются демо и пойдут в док

## Что зафиксировано реализацией iter65 (09.08.2026)

Тесты: `tests/unit/test_iteration65_assistant_ui.py` (42 шт.); регресс
iter58–64 — 318; UI-регресс кампании (iter19/20/23/26/52) — 43; демо: раздел
«iter65 · ДОК СПРАВА И КОНТЕКСТ ПО МЕСТУ».

1. **Фокус UI — ФАКТ о месте пользователя, а не разрешение отвечать по
   памяти.** Из фокуса берётся, что «эта ось» — это `DINP`
   (`resolve_question`), но границы всё равно считает `explain_node`: блок
   фокуса заканчивается этим ограничением ЯВНО. Иначе удобная подстановка
   стала бы лазейкой для выдуманных чисел.
2. **Поток публикует ОБЫЧНЫЙ словарь** (`campaign_ui.publish_ui_focus` →
   `st.session_state['ui_focus']`), а разбирает его ЧИСТАЯ функция
   `context.focus_from_state`. Поэтому, во-первых, «контекст по месту»
   проверяется тестом без запуска Streamlit, во-вторых, поток не тянет за
   собой слой ассистента ради одной записи.
3. **Страница показывает несколько секций сразу**, поэтому фокусом объявлена
   САМАЯ КОНКРЕТНАЯ из активных: пока база пуста — `seed` (единственная живая
   секция), дальше — выбранная ветка. Ручной селектор узла в доке лишь
   уточняет этот факт и НЕ перебивает то, что сказала секция.
4. **Подсказки шага генерируются, а не рисуются руками** (`suggested_questions`)
   и каждая маршрутизируется роутером iter64 — параметризованный тест по всем
   шагам требует, чтобы ни одна не попала в `clarify`. «Кнопка есть, а
   инструмента под неё нет» невозможно по построению.
5. **Подсказка без данных не исчезает, а ВЫКЛЮЧАЕТСЯ с причиной** («узел не
   выбран: разложите узел в спеке»). Пропавшая кнопка читалась бы как «здесь
   так спрашивать нельзя», хотя не хватает одного клика (A0.6).
6. **Ход — одна функция `run_turn`** для дока, демо и теста: сборка контекста,
   цикл инструментов, аудит, ответ в сессию. Расхождение «в демо работает, в
   интерфейсе нет» исключено конструкцией, а не дисциплиной.
7. **История хранит слова ЧЕЛОВЕКА, модель получает разрешённый вопрос**: в
   сессии остаётся «объясни эту ось», модели уходит «объясни ось DINP» +
   пометка фокуса. Переписывать сказанное человеком нельзя (через неделю
   непонятно, какую ось), гадать модели — тоже.
8. **Фокус и дайджест вложений живут ТОЛЬКО в сборке хода**, в сессию не
   пишутся: иначе вчерашнее место пользователя всплывало бы в завтрашнем
   разборе. Системный промпт архитектора при этом ровно один (`with_system`,
   iter64), а хвост диалога усечён по бюджету (iter58).
9. **Отказ модели/сети не роняет док**: `run_turn` возвращает `ok=False` с
   человекочитаемым текстом, вопрос остаётся в сессии. Стектрейс вместо
   ответа — худший из возможных вариантов «объяснения».
10. **Кнопка человека — единственный путь к классу `write`**: `human_apply` /

## iter71 — ПАКЕТ спеки: первичный ввод геометрии и её эволюция

**Багрепорт (живая сессия, 11.08.2026).** Ассистент собрал геометрию кампании
«кромка ПВХ» верно ЧИСЛЕННО (29 golden-проверок, Σphr 115,20–249,80, dim z = 16
— всё сошлось с ядром), но НЕ СМОГ отдать её в проект и честно написал: «канал
первичного ввода — только человек». Две причины, обе не в модели:

1. **инструмента не существовало.** `propose_patch` правит ПОЛЕ существующего
   узла и требует уже существующую спеку (`require_spec`), а добавление и
   удаление узла запрещены явно (`readonly.apply_patch_to_dicts`: «это смена
   схемы проекта, а не правка границы»). То есть первичный ввод и эволюция
   геометрии были невыразимы в принципе, а не «не разрешены».
2. **схема v2 модели не сообщалась.** Ни `spec_schema`, ни примера в промпте не
   было; формат приходилось восстанавливать по markdown-таблицам переписки. Итог
   предсказуем: JSON пришёл с ключами `components` / `groups` / `process` /
   `version` и `levels` внутри узлов — валидатор отверг его целиком, причём
   ПЕРВЫМ же сообщением, до ядра.

**Решение (выбор пользователя): полный канал — предложение пакетом, применение
кнопкой.** Канон iter63 не тронут: автор изменения геометрии — человек.

**Что зафиксировано реализацией: 46 тестов (`test_iteration71_spec_intake.py`),
регресс iter58–70 — 483**

1. **`spec_schema` (readonly)** — схема ИЗ ЯДРА: роли с обязательными и
   допустимыми ключами прямо из `_ROLE_TABLE`, инварианты (k=2 → ровно один
   `SHARE_CLOSURE`; k≥3 → только `SHARE_SIMPLEX`; closure/FIXED без диапазона;
   `members` точно совпадают; `group_order` — перестановка `GROUP_TOTAL`),
   рабочий ПРИМЕР и раздел `not_in_spec` (`levels`, `premix`, `process`,
   `version`, `components/groups`, legacy `lo/hi/of/to`) с указанием, где каждая
   сущность живёт на самом деле. Работает БЕЗ активной спеки — иначе первичный
   ввод снова упирался бы в её отсутствие. Тест проверяет, что пример
   собирается ядром: пример, который не собирается, хуже отсутствия примера.
2. **`validate_spec_package` (readonly)** — dry-run пакета целиком: сборка
   ядром, эффективные phr, `dim_z`, `spec_hash` и ДИФФ против текущей спеки
   (добавленные и удалённые узлы, смена ролей, съехавшие интервалы,
   `first_spec`). Отказ ядра возвращается РЕЗУЛЬТАТОМ с подсказкой, а чужая
   обёртка — `ToolError` с указанием на плоский `nodes`.
3. **`propose_spec` (propose)** — пакет в СТЕЙДЖ сессии (`StagedSpec`, статусы
   те же, что у патчей). Невалидный пакет в стейдж НЕ попадает: иначе человек
   нажимал бы «Применить» и получал ошибку вместо решения.
4. **`apply_spec` / `reject_spec` (write)** — только человек, только разовым
   токеном (`consent`: новые действия `apply_spec`/`reject_spec`). Токен
   привязан к пакету и к отпечатку спеки на момент нажатия; при первичном вводе
   `context_hash` пуст — подтверждается состояние «геометрии ещё не было».
   Токен от `apply_patch` для `apply_spec` не годится (проверено тестом).
5. **Гейты применения ЧЕСТНЫ** (`spec_package_gates`) — три случая различаются:
   * спеки не было → гейты неприменимы, и это сказано словами
     (`checked: False`, `reason`), а не выдано за «пройдено»;
   * состав компонентов изменился → прежние точки лежат в ДРУГОМ пространстве
     координат, гейт точек неприменим, но ставится `history_break` и громкое
     предупреждение: решение осознанное, а не молчаливое;
   * состав тот же (сменились роли/границы) → работают обычные гейты патча,
     сужение задним числом блокируется (тест: точка DINP = 13 phr).
6. **Журнал решений** — применение и отказ пишутся в `decision_log.jsonl` с
   `kind: apply_spec` / `reject_spec`, `first_spec`, `history_break`, обоими
   отпечатками и уровнем знания. Заголовок собирается ИЗ ДИФФА, а не из вольной
   формулировки.
7. **UI** — отдельная панель `🧬 Предложенные спеки (пакетом)` ВЫШЕ панели
   патчей (первичный ввод — первое, что делается в проекте), с таблицей
   («вид», «+узлы», «−узлы», «смена роли», «хеш»), РАСКРЫВАЕМЫМ JSON пакета
   (человек утверждает то, что может прочитать) и кнопками
   «Применить спеку» / «Отклонить спеку» через `context.human_apply_spec` /
   `human_reject_spec`.
8. **Промпт и маршрутизация** — `LIMITS_BLOCK` прямо требует брать формат из
   `spec_schema` и называет первичный ввод работой ассистента; `HUMAN_ONLY`
   пополнен `apply_spec`/`reject_spec`; добавлен golden-сценарий №9
   `spec_intake` и правило роутера ПЕРЕД `l1_widen` (иначе «добавь компонент до
   5 phr» уходило в патч по совпадению «до N phr», а патчем узел не добавить).
9. **Совместимость** — сессии без ключа `specs` (записанные до iter71)
   загружаются как раньше; `spec_hash` и сериализация спеки не тронуты (пакет
   без `group_order` даёт плоский список, как `to_dicts` до iter48).

**Замечание по нумерации:** номер iter70 уже занят разделом «ЧИСЛА» (см. выше),
поэтому этот шаг — iter71. Счётчик сценариев в

## iter73 — ПАКЕТ ПРОЕКТА: «Применить» рождает проект, а не молчит

**Багрепорт (живая сессия, 11.08.2026, продолжение iter71).** Ассистент собрал
геометрию кампании «кромка ПВХ» и положил пакет спеки в стейдж; человек нажал
«✅ Применить спеку» — и на закладке «🌱 Старт» НИЧЕГО не изменилось. При этом в
`decision_log.jsonl` легла запись `apply_spec` от «человек (UI)», а в
`session.json` пакет остался `staged`. Разбор нашёл ТРИ независимых дефекта:

1. **применять было НЕКУДА.** `apply_spec` пишет геометрию через
   `runner.set_phr_spec(...)` только `if runner is not None`, иначе результат
   уходит в `ctx.spec` — а он пересоздаётся на каждом прогоне Streamlit
   (`assistant_dock.dock_context`). Проекта в сессии не было
   (`project_campaigns/my_project/` содержал только `assistant/`, без
   `campaign.json`), поэтому применение исчезало вместе с прогоном.
2. **логическая ошибка канала (замечание пользователя).** phr-спека — это
   mixture-блок СХЕМЫ проекта: применение спеки при пустой сессии есть не правка
   проекта, а его РОЖДЕНИЕ. Инструмент же был написан как правка существующего и
   даже отказ формулировал так: «эволюция СХЕМЫ — её делает человек в сетапе».
   Одной спеки для рождения, однако, мало: `build_setup_runner` требует ещё
   ОТКЛИКИ и ПРОЦЕСС-ОСИ с границами, которых в спеке нет по схеме
   (`spec_schema.not_in_spec`) и которые нельзя выдумать за технолога (A0.6).
3. **состояние проекта нигде не заявлено (замечание пользователя).** Поле «Имя
   проекта» показывало `my_project` всегда — даже когда проекта не существовало;
   единственная явная надпись «Проекта в сессии нет» стояла НИЖЕ длинной формы
   сетапа; свёрнутость экспандера читалась как «уже заполнял». Кнопка
   «Применить» при этом выглядела активной.

**Решение (выбор пользователя, вариант «полноценная реализация возможностей
ассистента»): ПАКЕТ ПРОЕКТА.** Ассистент предлагает проект ЦЕЛИКОМ, человек
принимает кнопкой, а раннер собирает штатная кнопка «🏗 Построить проект» — путь
сборки проекта в приложении остаётся ОДИН.

**Что зафиксировано реализацией: 64 теста (`test_iteration73_project_intake.py`),
регресс iter58–72 — 512 + тесты кампании**

1. **`src/design/project_package.py` (ядро, без Streamlit)** — разбор пакета:
   блоки `spec` (состав) / `responses` (отклики) / `process` (оси с границами) —
   ОБЯЗАТЕЛЬНЫЕ, плюс `covariates`, `passport`, `seed`, `label`, `note`. Ключи
   верхнего уровня закрыты списком: опечатка в имени блока — ошибка, а не тихая
   потеря половины проекта. Отдельно ловятся промахи, наблюдавшиеся у модели:
   `levels: 3` вместо списка режимов (количество уровней — политика ПЛАНА),
   режим вне границ оси, вырожденная ось `[180, 180]`, пересечение имён
   компонентов / откликов / осей / ковариат (это столбцы ОДНОЙ базы).
2. **САМОДОКУМЕНТИРУЕМОСТЬ (требование пользователя: ввод идёт в несколько
   подходов)** — `package_manifest` отвечает «что именно загружается» ПО БЛОКАМ:
   состав (компоненты, узлы, dim z), отклики с единицами (`gloss [%]`), оси с
   границами и единицами (`T_plast 165…185 °C`), дискретные режимы, ковариаты,
   паспорт. «Сетки нет» сказано словами («все оси непрерывные»), а не пустой
   строкой. `project_package_schema` отдаёт формат как ДАННЫЕ с валидным
   примером (тест проверяет, что пример сам проходит разбор — урок iter71).
3. **Раннер собирает ТОЛЬКО штатная кнопка** — `package_to_setup_prefill`
   проецирует пакет в значения полей формы «🆕 Новый проект» (те же ключи, что
   у `setup_prefill_from_runner`, применяются через `setup_prefill_pending`).
   Ярлыки режима (`phr-спека (JSON)`, `JSON / файл`) дублируются в ядре строками
   и сверяются ТЕСТОМ с `campaign_ui`; текстовые поля читаются штатными
   парсерами (`parse_process_levels`, `parse_preflight_pairs`,
   `parse_process_links`, `parse_material_lots`, `parse_anchor_recipes`), а
   спека проходит round-trip по `spec_hash`.
4. **Инструменты** — `project_schema` и `validate_project_package` (readonly,
   работают БЕЗ проекта; отказ разбора — это `ok=False` с подсказкой, ход модели
   не падает), `propose_project` (propose → стейдж; невалидный пакет в стейдж не
   попадает), `apply_project` / `reject_project` (write, модели не выданы,
   разовый токен `apply_project`/`reject_project`, привязанный к `spec_hash`
   ПАКЕТА — активной спеки в этот момент нет по определению).
5. **`apply_project` не заводит проект поверх собранного** — иначе молча
   пропали бы измеренные точки и ветки; пакет остаётся в стейдже, кнопка в UI
   `disabled` с объяснением. Результат принятия — `setup_prefill` + `next_step`
   («поля заполнены, нажмите „Построить проект“»): молчать о недоделанном шаге
   нельзя, иначе исходный отказ повторится на другом экране.
6. **`StagedProject` в сессии** — ключ `projects` в `to_state`/`from_state`;
   сессии без него (до iter73) открываются как раньше. Пакетов может быть много:
   ввод идёт в несколько подходов, и таблица стейджа — история заходов.
7. **`context.persist_session`** — кнопки человека (патч, пакет спеки, пакет
   проекта) теперь СОХРАНЯЮТ сессию. До этого статус менялся только в памяти:
   применённый пакет на диске оставался `staged` и после перезапуска
   предлагался снова, хотя решение уже в журнале (дефект 3 из багрепорта).
8. **Видимость состояния** — `views.project_status_caption` рисуется ПЕРВОЙ
   строкой закладки «🌱 Старт» (`st.success` / `st.warning`, ДО экспандеров), а
   поле переименовано в «Имя проекта (для сохранения/загрузки)» с подсказкой,
   что это не признак открытого проекта. Живые `AppTest` проверяют оба состояния
   и наличие панели «🏗 Предложенные проекты» в доке.
9. **Промпт и маршрутизация** — сценарий №10 `project_intake`, правило роутера
   ПЕРЕД `spec_intake` («собери проект», «заведём кампанию», отклики рядом с
   осями), `HUMAN_ONLY` += `apply_project`/`reject_project`, `LIMITS_BLOCK`
   требует РАЗЛИЧАТЬ «нет проекта» и «нет спеки» и прямо запрещает выдумывать
   отклики и границы осей. Счётчик golden-сценариев в
   `test_iteration64_assistant_prompts.py` обновлён 9 → 10 осознанно.

**Что осталось за человеком (сознательно).** Сборку проекта запускает он же
кнопкой формы: пакет заполняет поля, но не подменяет решение. Отклики и границы
осей ассистент не придумывает — не назвали, вопрос идёт в `## OPEN_QUESTIONS`.

## iter76 — замкнутый круг НЕсобранного проекта (живая сессия 12.08.2026)

**Закрываемый отказ.** Пользователь принял пакет проекта, поля формы
заполнились — а дальше всё упёрлось в круг: «🏗 Построить проект» падал с
«Ось пары 'FILLER' не найдена среди координат полной схемы», «💾 Сохранить
проект» отказывал («проект ещё не собран»), помощник полей формы не видел и
точечно их править не мог, а смена имени проекта в поле «Имя проекта» молча
переключала переписку — выглядело как её потеря. Разбор дал ПЯТЬ дефектов:

1. **Ядро: группа спеки — валидная ось preflight-пары.**
   `set_preflight_pairs` валидировал имена только против листьев полной схемы,
   хотя тотал группы (`FILLER`, `SOFT`) — ровно сумма членов, то есть штатная
   «ось-сумма». Теперь имя узла-группы АКТИВНОЙ phr-спеки разворачивается в
   сумму членов (`PhrSpec.group_members()` — новый публичный метод); отказ на
   неизвестном имени перечисляет и координаты, и группы.
2. **Пакет проекта: пары паспорта валидируются на dry-run, а не на кнопке.**
   `parse_project_package` теперь прогоняет `passport.preflight_pairs` через
   `normalize_preflight_pairs` (компоненты спеки + процесс-оси пакета + группы
   спеки): неверное имя даёт `PackageError` уже в `validate_project_package` /
   `propose_project` — человек не утверждает кнопкой пакет, который потом не
   соберётся.
3. **Черновик настроек: «💾 Сохранить проект» работает ДО сборки.**
   При `ctrl is None` кнопка сохраняет снимок полей формы
   (`campaign_state.setup_draft_fields`, скаляры `setup_*`) в
   `project_campaigns/<имя>/setup_draft.json`. Такой проект виден в списке
   загрузки (`list_campaigns` считает проектом и черновик), «📂 Загрузить»
   возвращает поля через штатный `setup_prefill_pending`; сохранение
   СОБРАННОГО проекта удаляет устаревший черновик; `delete_campaign` удаляет
   и draft-only проекты.
4. **Помощник видит поля формы и правит их точечно.**
   Док кладёт снимок полей в `ToolContext.extra['setup_fields']`; появились
   инструменты: `get_setup_fields` (readonly), `propose_setup_fields`
   (propose — стейдж `StagedSetup` в сессии, ключ `setups`, совместимость со
   старыми сессиями), `apply_setup_fields` / `reject_setup_fields` (write,
   модели не выданы; consent-действия `apply_setup`/`reject_setup`).
   Принятие человеком (панель «📝 Предложенные правки полей» в доке) кладёт
   значения в `setup_prefill_pending` и пишет решение в журнал; проект
   по-прежнему собирает ТОЛЬКО кнопка «🏗 Построить проект». Промпт
   архитектора при `has_runner=False` говорит: смотри `get_setup_fields`,
   точечную правку заполненных полей предлагай `propose_setup_fields`, а не
   пакет проекта с нуля.
5. **Переписка не «пропадает» при смене имени проекта.**
   `dock_session` при смене имени показывает явное предупреждение
   (`K_SWITCH_MSG`): на какой проект переключились и где лежит прежний диалог.

Тесты: `tests/unit/test_iteration76_setup_circle.py` (34 шт.) — развёртка
групп в ядре и в пакете, dry-run отказ по неверной паре, round-trip черновика,
протокол `StagedSetup`, классы доступа новых инструментов, JSON-сериализуемость
снимка формы.

## iter77 — ИДЕНТИЧНОСТЬ проекта: ссылка вместо имени

**Багрепорт (замечание пользователя, 12.08.2026).** Проект и переписка
ассистента были связаны ЧЕРЕЗ ИМЯ: каталог назывался как строка из поля «Имя
проекта», а переписка лежала внутри этого каталога (`assistant/`). Отсюда три
следствия, и все — архитектурные, а не косметические:

1. правка одной буквы в поле имени = ДРУГАЯ переписка, другие вложения, другие
   журналы. iter76 умел лишь ПРЕДУПРЕДИТЬ об этом (`K_SWITCH_MSG`);
2. переименования проекта как операции не существовало вовсе — только «завести
   рядом ещё один каталог»;
3. не стартовавший проект (дефолтный `my_project`) идентичности не имел:
   подвязать к нему что-либо ДО сборки было нельзя, а опознавался он лишь по
   имени.

**Решение (вариант C, выбор пользователя): каталог остаётся человеко-читаемым,
идентичность лежит ВНУТРИ него, истинный ключ — `ref`.**

```
project_campaigns/<каталог>/
  project.json        # {"ref": "prj_…", "label": "…", "label_history": [...]}
  campaign.json       # движок (как было)
  setup_draft.json    # черновик формы несобранного проекта (iter76)
  assistant/          # переписка, вложения, журналы
```

Что зафиксировано реализацией (85 тестов
`tests/unit/test_iteration77_project_ref.py`):

1. **`src/core/project_ref.py` — ядро идентичности** (чистый stdlib: его
   импортируют и `assistant.store`, и `campaign_state`, и MCP). `ref` = `prj_` +
   12 hex, НЕизменяем; `label` меняется свободно; `dirname` стабилен.
   Резолв — сканом файлов (реестра-дубликата нет ⇒ рассинхрону нечего
   рассинхронизировать). Чтение диск не мутирует: ссылку выдаёт только явный
   `ensure_identity` / `migrate_root` (A0.6).
2. **Ссылка есть ДО старта.** `ensure_default_project` вызывается в
   `streamlit_app.main` при первом прогоне: дефолтный проект существует со
   ссылкой ещё без движка, поэтому переписка, вложения и черновик формы вяжутся
   к нему сразу. Не стартовавший проект открывается снова как дефолтный с ТОЙ ЖЕ
   ссылкой; прекратить его существование может только админское удаление
   (`delete_campaign` теперь принимает и проект, у которого есть лишь
   `project.json` или одна переписка).
3. **Переписка адресуется ссылкой.** `AssistantSession.ref` (пишется, только
   когда ссылка есть ⇒ round-trip старых сессий побайтно стабилен), функции
   `store.*_by_ref` (`load_session_by_ref`, `append_log_by_ref`, …),
   `dock.current_project(root)` берёт каталог из идентичности, а НЕ из
   `campaign_name`. Переименование проекта переписку не переключает — это и
   проверяет живой `AppTest`.
4. **Имя стало подписью.** В панели «📁 Проект» показана ссылка и папка,
   появилась кнопка «✏️ Переименовать проект» (меняет только `label`, прежние
   имена уходят в `label_history`). «💾 Сохранить проект» различает два смысла
   явно: то же имя → пишем в текущий проект по ссылке; другое имя → «сохранить
   как» (адресуем существующий или создаём НОВЫЙ проект с новой ссылкой и
   говорим об этом текстом).
5. **Одноимённые проекты допустимы.** Каталог получает суффикс (`Кромка (2)`),
   ссылки разные, переписки не сливаются. Резолв по имени при неоднозначности
   ОТКАЗЫВАЕТ («имя — не ключ») вместо догадки; точное имя каталога — уникальный
   адрес и разрешается.
6. **MCP-сервер** (`resolve_project`) принимает ссылку, имя каталога или
   `label`; `list_projects` отдаёт `ref` и `label` рядом с `project`.
7. **Миграция.** `migrate_root` при старте приложения выдаёт ссылки проектам,
   созданным до iter77: ничего не переносит и не переименовывает, только
   дописывает `project.json`; повторный вызов ничего не меняет. Проекты без
   ссылки видны как `legacy` — прятать существующие данные нельзя.
